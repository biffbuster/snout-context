# Current benchmark protocol

The next measurement is the [memory study](#memory-study) below. The sections after it record the completed 0.3.1 release regression and earlier plans.

## Memory study

Drafted 2026-10-23, frozen 2026-10-24 ([frozen inputs](#frozen-inputs) below): this section, the task lists, the Snout build, the harness, agent and model versions, prompts, budgets and grading. A change to any of them after that starts a new run.

**Question.** On real, related coding tasks from repositories we did not write, does Snout lower the cost per solved task, and does it lose solved tasks? Measured separately in Claude Code and in Codex.

**Arms.** Every task runs in a new session in every arm.

- `plain`: no Snout.
- `trim`: Snout's read gate and output trimming (enforce), memory off.
- `memory`: `trim` plus verified memory as built: a saved note is shown on the prompt it fits, with its source, once per session; nothing at session start; no automatic search of past sessions; agent-written lessons off.

Memory carries from task to task only in `memory`, oldest task first, from the run's own config folder. The harness records every note a session receives and fails the run if any reaches `plain` or `trim`.

**Amendment, 2026-10-27 (proposed; no session has run under it).** The owner moved memory from automatic notes to search the agent asks for: Snout offers a few current, cited records, and the agent decides what helps. A fourth arm tests that:

- `search`: `trim` plus memory recorded as built, automatic notes off, and Snout's MCP server given to the agent with two tools only, `snout_memory_search` and `snout_memory_fetch` (`snout mcp --tools`). The server's instructions say to search when the task may depend on how something was done, run or decided before, and to ignore what doesn't help. Before a chain's first session the harness starts that server and checks it offers exactly those two tools; a session in any other arm that calls one invalidates the run. Each session records the memory calls it made.
- **Question:** do agents with `search` solve the same tasks for fewer total tokens than with `trim`, and than with `plain`? Primary measure: total tokens (input including cached, plus output) and cost per solved task, paired by task; secondary: solved tasks (no loss allowed beyond the study's power), memory calls per session, and whether the sessions that searched differ from those that didn't.
- **Size:** first `trim` and `search`, one repeat, the 39 tasks per agent above (78 sessions per agent); then, if the owner approves, `plain` and a second repeat. A real one-session smoke per agent comes first, to confirm the agent can call the tools.
- The Snout build is the committed tree the run names; a change to the build, harness, arms or measures after the first session starts a new run.

**Amendment, 2026-10-28: the Gate 4 pilot (frozen before any session).** The pilot of [memory gates](memory-gates.md), gate 4, in place of the size plan above. Design file `bench/memory-pilot.json`; run with `bench/memory-study.mjs --pilot`, which refuses other arms, repeats or tasks.

- **Question:** on the same tasks, does memory add anything to trimming, and does the complete workflow lower the cost per solved task?
- **Arms:** `plain`, `trim` and `search`, as above. `search` now includes the session-start hint (`memoryHint`). When earlier sessions of the project are on record, one line at session start says how many, the latest one's date and agent, and how to search them. It shows nothing from the records. Only `search` has the hint; if it reaches another arm, that chain is invalid. The notes arm, `memory`, is not run.
- **Tasks:** the five oldest tasks of each list. Hugo: 15167, 15169, 15206, 15208 and 15245. vite: 23134, 23294, 23238, 23232 and 23355. hugo-15171, one of the five oldest, was excluded before any session: on this machine, two back-to-back grading checks of its reference fix differed, failing on a Tailwind test. Under the task rule a flaky task is excluded, so the next oldest, hugo-15245, takes its place. Every pilot task passed two grading checks on 2026-10-28. Memory carries within each repository's chain, oldest task first. A chain's first session has nothing on record and gets no hint. These are separate bug fixes, so memory can help only with what earlier sessions in the same repository learned, such as how to build and test and where the code lives. The [cross-agent handoff check](memory-gates.md#cross-agent-handoff-check-2026-10-28) tested a decision held only in a record; this pilot tests everyday use.
- **Sessions:** one repeat. That is 3 arms × 10 tasks = 30 per agent, 60 in all. Claude Code runs on the API with `--max-spend` at most $8 per repository, so $16 for the pilot (lowered to $6 in all by the 2026-10-29 amendment). Codex runs on the plan.
- **Order:** interleaved by task. Each task runs in all three arms before the next. The arm order rotates by task: `plain`, `trim`, `search`; then `trim`, `search`, `plain`; and so on. If arms ran one after another, the second arm's first session would start on a prompt cache the first arm had warmed. On these tasks a cache write is a real part of a session's cost. From now on this order applies to every run of `bench/memory-study.mjs`; the "Repeats" rule below still rotates by repeat.
- **Go/no-go,** per agent over both repositories (`pilotVerdict` in `bench/study-checks.mjs`, printed by `--summarize hugo.json,vite.json`).
  - There is no verdict if a chain is invalid, an arm is short of sessions, or the hint missed a `search` session that had records.
  - Otherwise memory adds value when `search` solves at least as many tasks as `trim` at a lower cost per solved task.
  - The complete workflow is `search` against `plain`, judged the same way.
  - Trimming is `trim` against `plain`, judged the same way.
  - If memory fails for both agents, it is fixed or removed before any larger run.
- **Reported, not gating:**
  - Total tokens, tool calls and minutes.
  - **Memory use**, from Snout's own log of each memory call: the sessions that searched, the searches that found nothing, and the records opened. A record counts as acted on when the session then used a file it names. That is a proxy, and it is reported as one (`memoryUse`).
  - **Wrong recalls:** a `search` session that opened a record, acted on it, and failed a task `trim` solved (`wrongRecalls`). Each is listed by name and reviewed before any full study.
  - In any arm but `search`, an answer from Snout's memory tools invalidates the chain.
- **After the pilot:** its ten tasks count as used before. The full study leaves them out, which keeps 15 Hugo and 13 vite tasks per agent. Ten tasks per agent can show a large effect but not estimate one, so the pilot supports no public claim.
- **Build:** pinned by its hashes in `bench/memory-freeze.json` (Snout bundle `51d7156a`), as the owner chose for the handoff check. This build includes the session-start pointer to unfinished work, search leaving out the calling session's own record, and the logging of memory searches and fetches that the measures above read. If the owner commits first, that commit carries the same hashes.

**Amendment, 2026-10-29: labels, the memory path and a $6 cap (before any paid session).** The owner asked that the pilot say why memory did or did not help, not only whether it did. Set in `bench/memory-pilot.json` before the first paid session:

- **Labels.** Each task is labeled before any session. A `candidate` is a task where an earlier task in the same repository changed files in a related folder: the same folder, its parent, or a sibling under a folder other than the root. That earlier record could help. Every other task is a `control`, and the first task of each repository always is. The folders come from the reference fixes, which no agent sees (`labelTasks`). Hugo has one candidate (15208, after 15167) and four controls. vite has four candidates and one control. A test holds the design file's labels to the rule.
- **The memory path,** for each `search` session: hint → search → a record from a labeled earlier task shown → opened → acted on → result. Each session's own records are listed, so a later search can be traced to the task that left the record (`memoryPath`). The arms are also split by label (`byLabel`). Reported, not gating.
- **What to work on next** (`memoryDiagnosis`). If agents got the hint and never searched, fix discovery. If they searched but no candidate acted on a labeled record, improve what memory captures, or choose more representative tasks. If they used a record but `search` cost more per solved task than `trim`, reduce retrieval overhead. A mixed result says which agent or task type needs work. It is not a reason to change the scoring afterwards.
- **Spend.** Claude Code is capped at $6 for the whole pilot. Hugo runs first with `--max-spend 3`, then vite with $6 minus what Hugo spent. A task's group, one session per arm, starts only if all three sessions fit the cap at the costliest session so far (`groupFits`), so every group that runs is complete. A run cut short this way is still scored on the groups it finished. The per-session check stays as a backstop.
- **No changes mid-run.** No code, prompt or setting changes once the first paid session starts.

**Agents and models.** Claude Code 2.1.306 with `claude-sonnet-5-5`, billed through the API from an empty config folder. Codex CLI 0.163.0 with `gpt-6.1-sol` at reasoning effort `low` on the owner's ChatGPT plan. The effort is set on the command line; before 2026-10-24 the harness took it from the owner's `~/.codex/config.toml`, which also says `low`. Codex still reads the rest of that file (MCP servers are overridden to none), so each run records its hash, its sandbox, approval and service-tier keys, and the plugins it enables. Claude Code and Codex rows are analyzed separately and never pooled.

**Contamination rule.** For each model, the cutoff its publisher states on the model's own page: `claude-sonnet-5-5`, training data cutoff June 2026 ([Anthropic models overview](https://platform.claude.com/docs/en/about-claude/models/overview)); `gpt-6.1-sol`, knowledge cutoff April 30, 2026 ([OpenAI model page](https://developers.openai.com/api/docs/models/gpt-6.1-sol)); both retrieved 2026-10-23. A cutoff given as a month means its last day. A model with no published cutoff uses its public release date. A task is eligible for a model only when its issue was opened, and its fix merged, at least 30 days after that model's cutoff. Both agents run the same list, so the window opens at the later date: 2026-07-30. Changing a model re-applies the rule.

**Repositories.** Two, neither ours nor a competitor's.

- `gohugoio/hugo` (Go), carried over from the real-repo study below.
- One TypeScript repository, chosen by rule: GitHub language TypeScript, at least 30k stars, MIT or Apache-2.0, Windows in CI, at least 30 issues in the window closed as completed with a linked PR; among those, the one with the most candidate tasks whose grading tests run without a browser or an outside service. Surveyed 2026-10-23: colinhacks/zod, honojs/hono, vuejs/core, nestjs/nest and vitejs/vite passed the first four conditions (TanStack/query, trpc/trpc, date-fns, mobx, react-hook-form, remix-run/react-router and others did not). Of those, hono, vuejs/core and vitejs/vite run CI on Windows, with 14, 16 and 22 such candidates. **vitejs/vite** is the repository.

**Task rule** (`bench/mine-tasks.mjs`, read-only GitHub API). An issue opened and closed as completed in the window, closed by a PR merged into the default branch in the window that changes at least one test file, 1 to 4 source files and at most 400 lines. Excluded before validation: tasks whose grading tests need a browser or an outside service (vite's `playground/` and `e2e/` tests). Then validated on this machine before any session: with only the PR's test files applied at its base commit, the tests load and at least one fails; with the whole PR, every one passes. Each check runs twice, and a task whose results differ between the two is excluded as flaky. Every drawn task is reported with its outcome; none is dropped after a session has run. Drawn 2026-10-23: 33 Hugo candidates; 22 vite candidates, 12 more excluded for browser tests (`bench/memory-tasks-hugo.json`, `bench/memory-tasks-vite.json`). Validated 2026-10-23 and 2026-10-24 (`bench/memory-validate.mjs`): **23 Hugo tasks** (excluded: 5 whose tests don't compile before the fix, 4 with no test failing before it, 1 flaky) and **18 vite tasks** (excluded: 4 where a test fails with the PR on this machine). Part of the first pass ran while other benchmark work loaded the machine, and that pass was stopped for low memory; every exclusion it could have caused (three "flaky" Hugo results and the four vite failures) was rechecked with the machine otherwise idle, one task at a time. One flaky result did not repeat (hugo-15171, now validated); the rest held. Excluded after validation, by a rule added 2026-10-24 before any study session: tasks used in any earlier real-agent run of ours. hugo-15234 and hugo-15253 ran in the realrepo smoke runs with Claude Code and Codex, and what those sessions saved led to a change in Snout's note writer, so they are not held out (field `usedBefore`). No other drawn task has run with a real agent. **39 tasks per agent** (21 Hugo, 18 vite), below the 56 the margin needs for 80% power, so this run can reveal large quality losses, not rule out a 10-point one.

**What the agent gets.** The issue's title, body and the comments posted before the fix PR was opened, as a frozen snapshot in the prompt (`bench/memory/<repo>/<issue>.issue.md`), with links to PRs, commits and branches removed. The same prompt in every arm, word for word:

> The repository in the current directory is `<owner/name>` at the commit just before the fix for the issue below. Find the cause and fix it by editing the source code. Run the relevant tests before you finish, and do not modify the existing tests. There is no network access: dependencies are already installed.
>
> `<issue snapshot>`

No MCP server and no web. The prompt names no test command: finding how tests run is part of the work memory can save.

**Workspaces** (`bench/memory-study.mjs`). Each task's workspace is prepared once: the base commit's files written out by git with no history, dependencies installed (Go modules; vite's pnpm packages through corepack's `pnpm`) and vite's own package built, then committed as the baseline. Before every session it is reset to that baseline, with installed dependencies kept and vite rebuilt. Claude Code works in a folder outside this repository, so none of its instruction files load. Codex runs a project's hooks only in a folder its user has trusted, so Codex workspaces sit inside this trusted checkout with no git repository of their own (the harness keeps it outside the folder), and `AGENTS.md` loading is off (`project_doc_max_bytes=0`). In Codex's `plain` arm, Snout's hooks are still present (they come from the trusted checkout) and run in observe mode with memory and the prompt tips off: they record and add nothing to the session.

**Hidden from the agent.** The fix and the PR's test files. The workspace is the base commit with no git history. The PR's tests are applied only for grading, after the session ends.

**Web access off.** Claude Code: WebFetch and WebSearch disallowed; shell commands that reach the network disallowed (curl, wget, gh, git fetch, pull, clone and push, npm and pnpm installs, `go get`, `go install`, `go mod download`); npm, pnpm and corepack forced offline and Go's module proxy off (`GOPROXY=off`). Codex: the workspace-write sandbox, whose network is off, and no live web search (it needs `--search`, which is never passed); the same offline settings. Dependencies are installed before the session starts. On Windows, Claude Code's shell is restricted by these rules, not by an OS sandbox, so every session's commands are scanned afterwards for network use, and each hit is reported.

**No Snout-side model, embedding or cloud calls.** This study tests local trimming and local verified memory, so nothing Snout runs may call a model or leave the machine. Every arm's config sets the prompt coach off (its `jev` mode sends prompts to TypeSafe), the preference judge off (Jev), lessons off, the repo map off and the shared hook server off. Each chain starts with a new, empty Snout config folder, so there is no Snout Cloud login and no embedding model to load (the model is not installed on this machine either); `SNOUT_TOKEN` and `TYPESAFE_API_KEY` are emptied for every session. The hooks are command hooks that run in their own process and reach no shared server. A watch (`bench/snout-guard.cjs`, preloaded through `NODE_OPTIONS`) records, for every Snout process and every process Snout starts, each socket connect, DNS lookup, `fetch`, child process, native addon and embedding-library import. Checked 2026-10-24 on real Snout hooks with no network involved: with the study's config, three hook events produced no Jev, cloud, embedding or network call; with Jev and cloud turned on and pointed at a closed local port, the watch caught one Jev call and one cloud sync.

**How the repository advances between tasks.** Within each repository, tasks run oldest merge first. Each task starts from its own fix's base commit: the repository as it stood upstream when the fix was written, the same in every arm. An agent's patch never carries to the next task. The only thing that carries is Snout's memory, in `memory`.

**Grading**, as in SWE-bench. FAIL_TO_PASS: the tests in the PR's test files that fail at the base with those files applied and pass with the whole PR. PASS_TO_PASS: the tests in those files that pass at both. A task is solved when, after the agent's patch and with the PR's test files applied, every FAIL_TO_PASS and every PASS_TO_PASS test passes. Go: `go test -json` on the packages those files are in. TypeScript: vitest's JSON reporter on those files. Grading runs outside the session, and Snout plays no part in it.

**Budgets and limits**, the same in every arm. One session per task with a 30-minute limit. Claude Code: $2.00 per session (`--max-budget-usd`). Codex: reasoning effort `low` and no dollar cap (it bills the plan). A session that hits a limit counts as attempted, not solved; its patch is still graded and the result recorded. A session the run started but never recorded, because the run was killed, is priced from its transcript and counted in spend, not scored.

**Repeats.** Two per task, arm and agent. Arm order rotates by repeat. Since the 2026-10-28 amendment, arms are interleaved by task within a repeat, and the order also rotates by task.

**Metrics.** Primary: cost per solved task, the cost of all attempts divided by the attempts solved. Claude Code: dollars, priced per call from the session transcripts at list prices (Sonnet 5.5: $2 input, $2.50 cache write, $0.10 cache read, $10 output per million tokens), checked against Claude Code's own cost figure for each session. Codex: tokens priced at `gpt-6.1-sol`'s list API prices and labeled as list-price equivalents, since the plan bills differently. Guardrail: the solved-task rate. Also reported: input, cached and output tokens, peak context, tool calls, wall time, and the notes each `memory` session received with their tokens.

**Analysis**, fixed before the sample size. Paired by task, `memory` vs `plain` and `trim` vs `plain`, and `memory` vs `trim` for memory's own part.

- Cost: the ratio of cost per solved task, with a 95% interval from a bootstrap over tasks, then repeats within each task. A saving is claimed only when the whole interval is below 1.
- Quality: the per-task difference in solved fraction. The non-inferiority margin is **10 percentage points**. Its one-sided 95% lower bound comes from the same bootstrap. "No loss larger than 10 points" is claimed only when that bound is above −10. Each task an arm fails that `plain` solves in the same repeat is listed by name.
- Sample size: assuming a standard deviation of 0.30 for the per-task difference (checked on the harness check below), 80% power at the 10-point margin needs about (1.645 + 0.842)² × 0.30² / 0.10² ≈ 56 tasks per agent. If fewer tasks validate, the run is reported as able to reveal large losses only, with the bound it achieved. The margin is not changed after results are seen.

**Decision rules.** Trimming stays only if `trim` vs `plain` lowers cost per solved task without crossing the quality margin. Memory stays only if `memory` vs `trim` does. Anything that fails is removed from the product.

**Validity.** A chain is marked invalid, and its rows are not scored, when a note reaches `plain` or `trim`, when Snout's hooks did not run in an arm that has them, when a `trim` or `memory` session's judged records show any mode but enforce (rows Snout measures but never judges, `tool-output` and `reversal`, say `observe` in every mode and are not counted), or when a session did not start, when the side-call watch records a Snout call to Jev, Snout Cloud, the embedding model or any non-local address, when the watch saw no Snout process in an arm with Snout's hooks (it did not load), or when it saw one in Claude Code's `plain` arm. Every command a session ran is scanned for network use, and each hit is listed in the results; an installed tool run through `npx` and a URL inside an edited string are not hits. In Claude Code, each session's tool calls are checked against Snout's hook heartbeats, and every call the hook missed is listed.

**Harness check**, never scored. Tasks from the same repositories by the same rule, merged before the window (2026-06-01 to 2026-07-29): the newest two per repository that validate (`bench/memory-check-hugo.json`, `bench/memory-check-vite.json`, field `checkSet`): hugo-15056, hugo-15086, vite-22796, vite-22944. Done 2026-10-23 with the stand-in agent, which applies the reference fix, for Claude Code and Codex: every arm solved every task, notes reached only `memory`, and the hooks ran in enforce in `trim` and `memory`. `--grade-check` confirmed on all four that an unrelated edit grades unsolved and the reference fix solved. A third validated task in each check file (hugo-15078, vite-22847) is outside the check set and is not run. A real check, one session per arm and agent on these four tasks (12 per agent), started 2026-10-24 with a $5 cap: 10 Claude Code sessions ran ($0.72 at list prices) before the run was stopped for low memory, and no Codex session ran. What it found, and the fixes, are in [memory gates](memory-gates.md), gate 1. The study runs only after all four gates there pass.

# Earlier protocols: Snout 0.3.1

This section records the completed 0.3.1 release regression and the measurements planned before the memory study. The [140-session Claude Code result](archive/0.3.1/claims.md) is a release regression on authored tasks; **no held-out 0.3.1 agent score has been recorded.** A [three-task Codex pilot](experiments/codex-gpt6-sol-2026-10-19/README.md) is diagnostic only. The older pre-registration, pilots, amendments, and results are preserved in the [historical protocol](archive/pre-0.3.1/benchmark-protocol.md). Their scores cannot be relabeled as current.

## Candidate and machine

Run on this Windows machine, from one frozen candidate. Record OS, Node, agent CLI and model versions; Snout package version, commit, dirty state, bundle SHA-256, and benchmark harness SHA-256. Install the same plugin and gate that users receive. An edited build, changed model, changed task prompt, or changed grading rule starts a new run; never append those rows to an earlier result. Preserve all attempts, errors, exclusions, and off/on order.

Before paid runs, pass `npm run verify`, inspect `npm pack --dry-run`, check the Claude Code and Codex hook contracts, and run a local install/hook smoke test. The strict claim check must pass against the current raw results cited in [claims.md](claims.md).

## Release regression run: internal coding tasks

`bench/ab.mjs` has 14 authored coding tasks. The clean release regression ran each on Claude Code with Snout off and enforce, five repeats per arm: 140 sessions. It exercised the shipped hook path, command output, MCP and memory interactions, and task completion with one model and identical $1.00 per-attempt budgets. The completed run recorded $13.3121 in API cost. The earlier $6.30 estimate and proposed $7 cap were planning figures, not the measured spend or authorization for another run. Obtain separate approval before any further paid run.

This fixture is useful as a release regression gate, but its tasks were written alongside Snout and are not a held-out estimate of typical repository savings. Report every task's off/on pass count, cost and attempts. A task that passes off and fails on is a headline regression. The principal efficiency metric is cost per solved task with a paired, task-bootstrap 95% interval; also report total spend, input/cache/output tokens, turns, Snout interventions, and recovery reads. A cost reduction requires the entire interval below zero. The predeclared no-quality-loss margin is −5 percentage points; its 95% lower bound must be above that margin. Merely equal point estimates or a small all-pass sample are not enough to imply general quality parity.

## Product score: held-out repository tasks

For the next product score, use the existing `bench/swe.mjs` task selection and official SWE-bench grader on repositories we did not author. Freeze selected task IDs, agent/model, Snout build, Docker image, prompts, per-session limits, exclusion rule, and quality margin before the pilot. Pair off/on attempts by task and repeat. The primary score is **cost per solved held-out task**, with a task-clustered 95% interval and the resolved-rate difference. Report Pass^k, timeout and recovery cost as secondary measures. A small capped pilot estimates feasibility and variance; scale to a confirmation run only if the pilot justifies the spend. Docker grading requires a working Docker/WSL2 or Mac setup on the machine that runs it. This Windows machine has Docker and the SWE Python environment, and a fake-agent official-grader smoke passed on one cached image; a live agent pilot remains pending.

## Real-repo study: Hugo (fixed 2026-10-21, before any run)

A held-out measurement on a popular repository we did not write, in a workflow that uses GitHub MCP. Harness: `bench/realrepo.mjs`; tasks: `bench/realrepo-hugo-tasks.json`.

**Repository rule.** Go or TypeScript, at least 30k stars and 100 MB, at least 30 issues closed as completed with a linked PR since 2026-08-01, Windows in CI, not a competitor. Of 23 repositories surveyed, five passed; gohugoio/hugo was chosen as the most-starred pass with the strongest Windows CI and a pure-Go build.

**Task rule.** Issues closed as completed since 2026-08-01, labeled Bug, closed by a merged PR into master that changed at least one `_test.go` or `testdata/` file, at most 4 non-test Go files and 400 changed lines. A task qualifies when, on this machine, with only the PR's test files applied at the base commit, those tests compile and at least one fails; with the whole PR it passes and no test fails. Tests that only fail to compile call code the fix adds, so they would grade a guess at its names; this condition was added on 2026-10-21 after the first draw admitted two such tasks (#15444, #15403) and before any session ran. The newest 10 qualifying issues are the task set. Every drawn task is reported; none is dropped after a run.

**Session (primary: long sessions, `--chain`).** Snout's target is long working sessions, where tokens kept out early are saved again on every later call and compaction can lose facts. So the primary run puts all 10 issues, oldest first, into ONE Claude Code session per arm and repeat: each issue in its own folder at its PR's base commit with no git history, the session resumed for each next issue, Claude Code's own auto-compact point, the advisor tool off. Claude Code, Sonnet, billed through the API, empty config folder. The agent reads each issue through GitHub's MCP server (read-only, issues tools only), so it cannot open the fix PR or write anything upstream. Same prompts, model, tools, $3.00 budget and 30-minute limit per issue in both arms; an issue that hits the limit counts as attempted and the session moves on (three end the run as an infrastructure failure). Arms: Snout `off` (observe: records, changes nothing) and `enforce` (trimming and the read gate; since 0.3.2 Snout adds nothing after a compaction). Whether memory and notes are on in either arm is not yet fixed: `bench/realrepo.mjs` does not set it, and it must be decided, with the planned third arm (a fresh session per issue with notes), before any run. Three repeats per arm, arm order alternating by repeat. A run in which Snout records nothing halts. The single-issue mode (one session per issue) stays available as a diagnostic, not the headline.

**Grading.** After the session the PR's test files replace the workspace's copies and the packages they touch run with `go test -json`. Resolved: every fail-to-pass test passes and no pass-to-pass test fails. Snout plays no part in grading.

**Analysis.** Cost is priced per call from each session transcript, so every issue's share of its session is known. Primary: cost per solved issue, enforce vs off, with a paired 95% interval from a bootstrap over issues and then runs within each issue. Also: resolved issues per arm; total cost, peak context and compactions per session; first-half vs second-half cost and resolved counts (late in a session is where trimming should compound and compaction can lose facts); tokens Snout kept out, by source (MCP, command output, reads); recovery reads. With 10 unique issues the exact zero-harm lower bound is about −26 points, so this run can support a cost claim but **not** a no-quality-loss claim at the −5 point margin, which needs about 60 issues. A paid run needs the owner's approval with its session count and cost cap.

**Product test (fixed 2026-10-22, before any run; replaces the two-arm design above as the headline).** The two-arm run turned on trimming and the read gate only, in one long session, so it could not test what Snout is for: sessions that start fresh and still know what earlier ones learned. Three arms, same 10 issues oldest first, same prompts, model, tools, budget and limits:

- **A `plain`:** one long session for all issues, no Snout. How most people work today.
- **C-off `plain-fresh`:** a new session per issue, no Snout. What starting fresh alone gives.
- **C-on `snout-fresh`:** a new session per issue, Snout as a user installs it (the plugin's own hooks, enforce, memory on): notes written at the end of each session reach the next one.

Each run gets its own Snout config folder, so notes come only from earlier issues in the same run; the harness records the notes each session received and warns if notes reach an arm without Snout memory. Sessions run against an empty Claude Code config folder, on an API key (`--api`) or the owner's own plan (`--plan`, via `claude setup-token`); either way cost is priced per call from the transcripts at list prices.

Decision rules, written before any run:

1. **Headline:** cost per solved issue, C-on vs A, with the paired 95% interval (bootstrap over issues, then runs). A savings claim needs the interval entirely below zero and C-on solving at least as many issues as A, or one fewer at most.
2. **Snout's own part:** C-on vs C-off. If C-on is not cheaper per solved issue or does not solve more, the saving belongs to starting fresh, not to Snout, and we say so.
3. **Quality:** solved issues per arm and Pass^k, reported for every arm. With 10 issues no "no quality loss" claim is made.
4. **Validity:** a run where notes reached no later session in C-on, or reached any session in A or C-off, is reported as a harness failure and not scored.

Order: a free dry run with the stand-in agent (done 2026-10-22, all checks passed), then a two-issue smoke run of all three arms to confirm the real agent reads issues, Snout acts and notes carry over, then the full run of 10 issues × 3 arms × 3 repeats, each step approved with its session count.

## Codex and memory

Run Codex on its own matched off/on task set. Under a plan, its effective-token measure is a proxy, not a dollar bill; never combine Codex and Claude rows into one effect estimate. Run compaction and cross-agent recall as separate quality evaluations with same-set, current-build rows, including facts retained, false recalls, and task outcome. The older 66%→97% retention figures came from different sets and cannot be a 0.3.1 claim.

## Publication standard (fixed 2026-10-13)

Publish only a complete, version-stamped, reproducible result. A savings claim requires the paired 95% interval for cost per solved task entirely below zero. A no-quality-loss claim requires the 95% lower bound for the resolved-rate change above the predeclared margin, and all material regressions and exclusions must be visible. Keep the raw JSON and derived attempts CSV, summary JSON, and chart in the repository. Cite each current result from [claims.md](claims.md). Historical results remain labeled as historical in the [archive](archive/pre-0.3.1/README.md).

For an all-pass paired set, the ordinary task bootstrap has a misleading zero-width quality interval. The reporter instead uses a one-sided 95% exact zero-harm lower bound based on the count of unique tasks, not repeated attempts: `100 × (0.05^(1/tasks) − 1)` percentage points. This is a conservative quality gate for small all-pass samples; the paired task bootstrap still supplies the efficiency interval. Historical reports are frozen with their original analysis.
