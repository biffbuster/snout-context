### Any additional comments?

I encountered this bug working on one of my projects. The analysis and root cause below have been worked out by AI. However, I confirm I've checked the reproduction and details above are correct.

### Root cause

In `packages/compiler-core/src/transforms/vFor.ts`, the `v-memo` + `v-for` loop builder emits the item's `:key` expression directly into the cache guard without wrapping it in parentheses:

```ts
loop.body = createBlockStatement([
  createCompoundExpression([`const _memo = (`, memo.exp, `)`]),
  createCompoundExpression([
    `if (_cached && _cached.el`,
    ...(keyExp ? [` && _cached.key === `, keyExp] : []),
    ` && ${context.helperString(IS_MEMO_SAME)}(_cached, _memo)) return _cached`,
  ]),
  // ...
]);
```

Because `?:` has **lower precedence** than `&&`, a ternary key makes the generated condition parse as:

```js
(_cached && _cached.el && ((_cached.key === item.kind) === 'a'))
  ? item.a
  : (item.b && _isMemoSame(_cached, _memo))
```

The `_isMemoSame(...)` call therefore falls into the **else branch of the ternary** instead of being part of the guard. On the first render `_cached` is `undefined` (the `_cache` slot is empty), the condition is falsy, and `_isMemoSame(undefined, _memo)` is invoked — `isMemoSame` then reads `cached.memo` on `undefined`.

Any low-precedence `:key` expression triggers this: ternary (`a ? b : c`), logical (`a || b`, `a ?? b`), assignment, etc. Only higher-precedence keys (identifiers, member expressions, call expressions) happen to compile to a correctly-parsed guard — which is why the [documented example](https://vuejs.org/api/built-in-directives.html#v-memo) (`:key="item.id"`) works and this slipped through.

The [docs](https://vuejs.org/api/built-in-directives.html#v-memo) only require `v-memo` and `v-for` to be used on the same element (they are, here) and place no restriction on the `:key` expression, so this is within the documented usage.

This appears to be a sibling of [#14859](https://github.com/vuejs/core/issues/14859) (the `<template v-for>` + non-identifier key + `v-memo` compile-time crash); both stem from the eager key handling added in [#12014]([link removed]) (commit `99009ee`, released in 3.5.13 — so this is likely present from 3.5.13 onward, and the offending code is still on `main`).

### Suggested fix

Wrap the key expression when generating the guard:

```ts
...(keyExp ? [` && _cached.key === (`, keyExp, `)`] : []),
```

which yields:

```js
_cached && _cached.el && _cached.key === (item.kind === 'a' ? item.a : item.b) && _isMemoSame(_cached, _memo)
```

A compiler snapshot test for `v-for` + `v-memo` + a ternary `:key`, plus a runtime test that mounts without throwing, would cover the regression.

### Workaround

Move the key expression into a function or member expression so the emitted guard has the correct precedence, e.g. `:key="rowKey(row)"`.
