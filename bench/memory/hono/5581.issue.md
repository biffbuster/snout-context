# Cookie prefix checks are case-sensitive, so `__host-` / `__secure-` cookies skip validation (issue #5581)

### What version of Hono are you using?

main (5ca49b07)

### What runtime/platform is your app running on? (with version if possible)

Any. It's in `src/utils/cookie.ts` and doesn't depend on the runtime (reproduced on Node 24).

### What steps can reproduce the bug?

```ts
import { serialize } from 'hono/utils/cookie'

serialize('__Host-sid', 'v')   // throws: __Host- Cookie must have Secure attributes
serialize('__host-sid', 'v')   // returns "__host-sid=v"
serialize('__secure-sid', 'v') // returns "__secure-sid=v"
```

The same applies to `setCookie(c, '__host-sid', ...)`.

### What is the expected behavior?

Throw the same errors as for `__Host-` / `__Secure-`.

rfc6265bis-22 section 5.4 says "UAs MUST match cookie name prefixes case-insensitively", and the storage model (section 5.7, steps 20–21) makes the browser ignore a `__secure-` cookie without Secure and reject a `__host-` cookie that lacks Secure / Path=/ or has a Domain. Hono's check exists to catch cookies the browser refuses, but with a different capitalization (`__host-`, `__secure-`) the cookie is silently dropped by the browser.

### Root Cause
In `src/utils/cookie.ts` (`_serialize`, lines 180–198), cookie prefix checks use case-sensitive `name.startsWith('__Secure-')` and `name.startsWith('__Host-')`. Per RFC 6265bis Section 5.4, user agents match `__Secure-` and `__Host-` prefixes case-insensitively, so lowercase/mixed-case prefixes bypass server-side validation in Hono and get rejected by browsers.

### Proposed Fix
Normalize `const lowerName = name.toLowerCase()` and check `lowerName.startsWith('__secure-')` and `lowerName.startsWith('__host-')`:
```diff
+  const lowerName = name.toLowerCase()
   let cookie = `${name}=${value}`
 
-  if (name.startsWith('__Secure-') && !opt.secure) {
+  if (lowerName.startsWith('__secure-') && !opt.secure) {
     // https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22#section-4.1.3.1
     throw new Error('__Secure- Cookie must have Secure attributes')
   }
 
-  if (name.startsWith('__Host-')) {
+  if (lowerName.startsWith('__host-')) {
```

Comment by visualkhh:

Verified the browser half in Chromium, since that determines whether this is a theoretical nit or silent data loss — it's the latter. (Context: the server framework I use ([@dooboostore/simple-boot-http-server](https://www.npmjs.com/package/@dooboostore/simple-boot-http-server)) reads request cookies today but has no `Set-Cookie` serializer yet — this thread is now my spec reference for prefix handling when it's added.)

**Browser (http origin, `document.cookie` assignment).** Setting `__Host-sid`, `__host-sid`, `__Secure-sid`, `__secure-sid` (all without `Secure`) plus a `plain` control, then reading back:

```
plain=v
```

All four prefixed variants are silently dropped regardless of capitalization; only `plain` survives. So the case-insensitive matching in RFC 6265bis §5.4/§5.7 is real engine behavior, and any `__host-`/`__secure-` cookie Hono serializes without `Secure` never reaches the browser's jar — exactly the reported hazard.

**Source.** `src/utils/cookie.ts` L180-196: the runtime guards are `name.startsWith('__Secure-')` / `startsWith('__Host-')` (case-sensitive), and the `__Host-` branch is otherwise complete (`Secure` + `Path=/` + no `Domain`). So lowercasing before the two `startsWith` checks, as the linked forks do, closes the runtime gap.

One level the forks miss: the *type* constraints at L31-33 (`Name extends \`__Secure-${string}\`` → requires `secure: true`) are also case-sensitive — template-literal matching doesn't fold case. So `setCookie(c, '__secure-sid', 'v')` type-checks today with no `Secure` requirement, and keeps type-checking after a runtime-only fix. A complete fix needs the type side too (e.g. matching on `Lowercase<Name>`), plus tests pinning the lowercase variants at both levels.
