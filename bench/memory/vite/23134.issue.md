# `build.lib` without `entry`: a second build with a different `input` still builds the first entry (issue #23134)

### Describe the bug

When `build.lib` is set without an `entry`, resolving the config writes the top-level `input` into the user's own `lib` object. If the same config object is used again for another build with a different `input`, the new input is silently ignored and the first entry is built again.

### Reproduction

https://stackblitz.com/edit/vitejs-vite-uscwzq3e?file=repro.mjs

### Steps to reproduce

```sh
mkdir lib-repro && cd lib-repro
pnpm init
pnpm add -D vite
mkdir src
echo "export const who = 'I am A'" > src/a.js
echo "export const who = 'I am B'" > src/b.js
```

`repro.mjs`:

```js
import { build } from 'vite'

const shared = {
  logLevel: 'error',
  configFile: false,
  build: {
    lib: { formats: ['es'] }, // no entry, falls back to the top-level `input`
  },
}

await build({ ...shared, input: 'src/a.js' })
console.log('user lib object after first build:', shared.build.lib)

const result = await build({ ...shared, input: 'src/b.js' })
console.log('second build output:\n' + result[0].output[0].code)
```

Run `node repro.mjs`. Actual result:

```
user lib object after first build: { formats: [ 'es' ], entry: 'src/a.js' }
second build output:
//#region src/a.js
var e = "I am A";
//#endregion
export { e as who };
```

Expected: the user config object is not modified, and the second build bundles `src/b.js` (`I am B`).
