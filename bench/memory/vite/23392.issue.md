# vite.config change during an in-flight config restart is silently dropped, leaving the server running a config that no longer matches disk (issue #23392)

### Describe the bug

When `vite.config.ts` changes, the dev server restarts itself. If the config file changes again while that restart is still in flight, the second change is silently dropped: `server.restart()` guards with `_restartPromise` and returns the in-flight promise instead of queueing a follow-up restart.

```ts
async restart(forceOptimize?: boolean) {
  if (!server._restartPromise) {
    server._forceOptimizeOnRestart = !!forceOptimize
    server._restartPromise = restartServer(server).finally(() => {
      server._restartPromise = null
      server._forceOptimizeOnRestart = false
    })
  }
  return server._restartPromise
}
```

The dropped call represented a newer config on disk. After the in-flight restart completes, the server is running a config snapshot that no longer matches `vite.config.ts`, and since the file does not change again, nothing ever triggers the missing restart. The server stays wrong until the developer intervenes (touch the config file, press `r`, or kill and relaunch).

The window is the full duration of `restartServer()`, which includes a complete `_createServer()`: config resolution, plugin init, framework plugin startup. With a framework plugin like SvelteKit this is multiple seconds, so it is easy to hit in practice. The common real-world trigger is `git checkout` between branches whose `vite.config.ts` differ: switching to an older branch and back within a few seconds leaves the server running the older branch's config while disk has the newer one. I hit this repeatedly in the Open WebUI repo, where a recently added `server.proxy` block would silently vanish after branch switching, killing every `/api` request until a manual restart.

The log shows the drop clearly, two config change notices but only one completed restart:

```
4:02:06 AM [vite] vite.config.ts changed, restarting server...
4:02:07 AM [vite] vite.config.ts changed, restarting server...
4:02:09 AM [vite] server restarted.
```

What I expect: a `restart()` requested while a restart is in flight should be coalesced into one follow-up restart after the current one completes (a pending flag would do), so the server always converges to the config on disk.

For context, #21636 and #21810 recently hardened this guard by closing loopholes that allowed a second concurrent restart to start. That made the drop airtight, but the dropped request can represent a newer config, which is the case this report covers.

### Reproduction

https://github.com/silentoplayz/vite-restart-race-repro

### Steps to reproduce

```
npm install
npm run repro
```

The script starts a tiny JSON backend on `:9876` and `vite dev` on `:5199` with a config that proxies `/api` to the backend. The config includes a plugin whose `config()` hook awaits 3 seconds, simulating slow framework plugin startup so the race window is deterministic. The script then:

1. Confirms `/api` returns the backend JSON through the proxy.
2. Overwrites `vite.config.ts` with a variant without the proxy (restart #1 begins).
3. One second later, while restart #1 is still in flight, restores the config with the proxy.
4. After everything settles, `vite.config.ts` on disk contains the proxy, but `/api` returns the SPA fallback HTML: the server is running the proxy-less snapshot.
5. As a control, a single `touch vite.config.ts` restarts correctly and `/api` works again.

Comment by santusht06:

Thanks for the detailed report and reproduction repo @silentoplayz!

Can confirm this race condition:
1. When a config change triggers `server.restart()`, `_restartPromise` is held for the duration of `restartServer(server)`.
2. Any subsequent config change (e.g. from switching git branches back and forth) arriving while `_restartPromise` is in-flight returns the existing promise without recording that a newer config was written to disk.
3. The server finishes restart #1 and remains on the stale config snapshot indefinitely.

Fixing this by tracking pending restart requests and looping in `server.restart()` so any in-flight changes trigger a follow-up restart before settling, ensuring the server always converges to the latest configuration on disk. Submitting a PR with the fix and regression test shortly.
