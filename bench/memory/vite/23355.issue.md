# `build.license` attributes the wrong version and omits license text for packages with nested `package.json` type markers (issue #23355)

### Describe the bug

`build.license` resolves each bundled module to its package via
`findNearestMainPackageData`. For packages that ship a dual ESM/CJS build with a bare
type-marker `package.json` in a subdirectory, resolution stops at the marker instead of
the real package root. The emitted license file then reports `0.0.0` as the version and
carries no license text or SPDX identifier for those packages.

This matters more than a normal metadata glitch: the output of this option is an
attribution notice. A file that names a dependency with a fabricated version and no
license text does not discharge the notice clause it exists to satisfy, and it fails
silently — there is nothing in the output to indicate the entry is incomplete.

### Reproduction

Any package with this layout reproduces it. `socket.io-client` and its transitive deps
are a convenient case:

```
node_modules/engine.io-client/package.json              → name, version 6.6.3, license MIT, LICENSE file
node_modules/engine.io-client/build/esm/package.json    → {"name":"engine.io-client","type":"module","browser":{…}}
```

With `build.license` enabled and `socket.io-client` imported, the emitted file contains:

```
## @socket.io/component-emitter - 0.0.0     (actual: 3.1.2, MIT)
## engine.io-client - 0.0.0                 (actual: 6.6.3, MIT)
## engine.io-parser - 0.0.0                 (actual: 5.2.3, MIT)
## socket.io-client - 4.8.3                 (version correct; no identifier, no text)
```

`socket.io-client` differs because its own marker happens to include `version`.

### Root cause

`findNearestMainPackageData` recurses upward only while `name` is absent:

```js
function findNearestMainPackageData(basedir, packageCache) {
  const nearestPackage = findNearestPackageData(basedir, packageCache);
  return nearestPackage && (nearestPackage.data.name
    ? nearestPackage
    : findNearestMainPackageData(path.dirname(nearestPackage.dir), packageCache));
}
```

A type-marker manifest carrying `name` but no `version` satisfies that predicate, so it
is treated as the main package data. The license plugin then reads
`{ name, version = '0.0.0', license }` from the marker and looks for a license file in
the marker's directory, where there isn't one.

### Suggested fix

Requiring `version` as well as `name` before accepting a manifest as the main package
data would resolve it. If tightening the shared helper is undesirable — other callers may
legitimately want a name-only match — the license plugin could keep walking upward while
`version` is missing, or resolve the package root from the last `node_modules/` path
segment instead.

Either way it would be worth having the plugin surface incomplete entries rather than
emitting them, since the failure is otherwise invisible in the output.

Related precedent: #19324 handled the adjacent case of a `package.json` without `name`
reaching `resolveLibCssFilename`. This is the `name`-without-`version` variant, surfacing
in a different consumer.

### Environment

Observed on `vite@7.3.1` and on a Rolldown-based Vite 8 distribution; the plugin
implementation is identical in both. pnpm 10.11.1, Node 22, Linux.
