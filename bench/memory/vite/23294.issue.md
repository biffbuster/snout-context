# CSS minify: `build.target: "esnext"` passes `targets: {}` to Lightning CSS, which reads it as "nothing is supported"

**Vite:** 8.2.0
**Affects:** `build.cssMinify` default path (Lightning CSS)

## Description

With `build.target: "esnext"` (and therefore `build.cssTarget: "esnext"`), Vite calls Lightning
CSS with `targets: {}` rather than `targets: undefined`.

Lightning CSS treats an empty targets object differently from an absent one: `{}` means "no
browser supports anything", so compatibility lowering runs. `undefined` means "no constraints"
and leaves modern syntax alone. Users who set `esnext` are explicitly asking for the latter.

`convertTargets` skips `esnext` entries and returns the accumulated object, which for a
target list of exactly `["esnext"]` is `{}`:

```js
for (const entry of entriesWithoutES) {
  if (entry === "esnext") continue;
  // ...
}
return targets; // {} when every entry was "esnext"
```

`minifyCSS` then passes that straight through:

```js
targets: convertTargets(config.build.cssTarget),
```

## Impact

Two problems:

1. `esnext` users get compatibility transforms they opted out of.
2. It exposes them to a Lightning CSS bug where rules are silently dropped —
   see https://github.com/parcel-bundler/lightningcss/issues/1310.

In our case this silently deleted three CSS rules from a production build. The pattern was:

```css
.card:hover { --icon-bg: blue }
.card:hover,
.card:open:not([data-closing]) { --bg: gray }
```

The `:open` half disappeared from the minified output with no warning. Dev was fine, so it
went unnoticed. Switching to `build.cssMinify: "esbuild"` restored it.

## Suggested fix

Pass `undefined` when the converted targets object has no keys:

```js
const converted = convertTargets(config.build.cssTarget)
targets: Object.keys(converted).length ? converted : undefined,
```

That makes `esnext` mean "no constraints" for CSS, matching what it means for JS.

## Note

`build.cssMinify: "esbuild"` is a working workaround, but esbuild is only an *optional* peer
dependency of Vite 8. Projects relying on it need to declare it themselves, or the escape
hatch breaks whenever a transitive dependency stops providing it.

## Related

`convertTargets` was previously fixed for unknown ES-year targets in #17983. That fix
extended the ES-to-browser map; it does not cover `esnext`, which still yields `{}`.
