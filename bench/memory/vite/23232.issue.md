# SSR transform: imported binding used as a computed key in a defaulted destructured parameter is not rewritten (ReferenceError) (issue #23232)

*__Note:__ This issue was written by my clanker. While I try to verify its steps as much as possible, it might not be 100% correct.*

---

### Describe the bug

Under SSR (`ssrLoadModule` / vite-node / any SSR build), when an **imported binding** is used as a **computed key** inside a **destructured function parameter that has a default value** (`function f({ [KEY]: v } = {}) {}`), the SSR transform fails to rewrite the reference to the import namespace. At runtime the identifier is a bare reference and throws `ReferenceError: KEY is not defined`.

The same code works when the parameter has **no default** (plain `ObjectPattern`), and when the destructuring is moved into the function body (`const { [KEY]: v } = input`). Only the defaulted-parameter form (`AssignmentPattern`) is affected.

### Reproduction

Three files:

```js
// data.js
export const KEY = 'k';
```
```js
// mod.js
import { KEY } from './data.js';
export function make({ [KEY]: value = null } = {}) {
  return { [KEY]: value };
}
```
```js
// repro.mjs
import { createServer } from 'vite';
const server = await createServer({
  root: new URL('.', import.meta.url).pathname,
  server: { middlewareMode: true },
  appType: 'custom',
  logLevel: 'silent',
});
const mod = await server.ssrLoadModule('./mod.js');
console.log(mod.make()); // ReferenceError: KEY is not defined
await server.close();
```

`node repro.mjs` -> `ReferenceError: KEY is not defined`.

### Expected

`make()` returns `{ k: null }`. The computed key `KEY` should be rewritten to the import namespace access, exactly as it is in every non-parameter position.

### Root cause

In the SSR transform's identifier walker (`ssrTransform`), function parameters are handled two ways:

- A parameter that is directly an `ObjectPattern`/`ArrayPattern` goes through `handlePattern`, which recurses only into each property's **value** and correctly ignores computed keys.
- A parameter that is an `AssignmentPattern` (i.e. has a default) is instead walked generically, calling `setScope(...)` for the identifiers it encounters. The only property-key guard there is `isStaticPropertyKey(child, parent)`, which returns `true` **only for non-computed keys**. So a **computed** key (`[KEY]`) falls through and is registered as a locally-scoped binding.

Once `KEY` is in the function scope, the later rewrite pass treats it as a local and skips the import rewrite, leaving a bare `KEY` -> `ReferenceError`.

### Proposed fix

In the parameter walker, skip any property key that is not the property value (both static and computed), mirroring `handlePattern`. For example, replace the `isStaticPropertyKey(child, parent)` guard with:

```js
if (parent?.type === 'Property' && parent.key === child && parent.value !== child) return;
```

This keeps shorthand bindings (`{ x } = {}`, where `key === value`) correctly scoped, stops computed keys from being scoped, and lets the normal rewrite handle them. Verified against the minimal repro above (throws before, returns `{ k: null }` after).

### System info

- Reproduced at runtime on `vite@7.1.12`; the same code path is present unchanged in `vite@7.3.6` and `vite@8.2.1`.
- Node.js 24, SSR (`ssrLoadModule`). Also surfaces via vite-node and Vitest.

Comment by yigiterturk-dev:

The report checks out. Reproduced on `vite@8.2.1` / Node 24 with the exact repro, and the proposed fix holds up under a scoping regression pass.

### Confirmed, and the trigger is narrower than "has a default"

Looking at the emitted SSR code rather than just the runtime error makes the boundary exact — it is a default on the **parameter**, not on the property:

| source | emitted | result |
| --- | --- | --- |
| `function f({ [KEY]: v = null } = {})` | `{ [KEY]: v = null } = {}` | ReferenceError |
| `const f = ({ [KEY]: v = null } = {}) =>` | `{ [KEY]: v = null } = {}` | ReferenceError |
| `function f({ a: { [KEY]: v } = {} } = {})` | `{ a: { [KEY]: v } = {} } = {}` | ReferenceError |
| `function f([{ [KEY]: v } = {}] = [])` | `[{ [KEY]: v } = {}] = []` | ReferenceError |
| `class C { m({ [KEY]: v } = {}) {} }` | `{ [KEY]: v } = {}` | ReferenceError |
| `function f({ [KEY]: v })` | `{ [__vite_ssr_import_0__.KEY]: v }` | ok |
| `function f({ [KEY]: v = null })` | `{ [__vite_ssr_import_0__.KEY]: v = null }` | ok |
| `function f(o) { const { [KEY]: v } = o }` | `{ [__vite_ssr_import_0__.KEY]: v }` | ok |
| `function f() { return { [KEY]: 1 } }` | `{ [__vite_ssr_import_0__.KEY]: 1 }` | ok |

So a property-level default is fine; it is the parameter being an `AssignmentPattern` that routes it away from `handlePattern`. Worth noting the blast radius is a bit wider than the original report: arrow functions, class methods, nested patterns and **array** patterns are all affected, not only top-level object patterns.

### Call site

`walk$1(p.type === "AssignmentPattern" ? p.left : p, ...)` in the parameter branch of `ssrTransform`, where the only key guard is:

```js
if (isStaticPropertyKey(child, parent)) return;
```

and `isStaticPropertyKey = (node, parent) => parent && isStaticProperty(parent) && parent.key === node`. `isStaticProperty` requires a non-computed key, so `[KEY]` falls through to `setScope(node, child.name)` and is registered as a local binding. The rewrite pass then leaves it bare.

### The proposed fix works, including the shadowing cases

Patching that one guard to:

```js
if (parent?.type === "Property" && parent.key === child && parent.value !== child) return;
```

turns all five broken rows above into the rewritten form. The risk with that change is over-skipping and breaking shorthand bindings, so I checked the shadowing side explicitly — with `export const KEY = 'IMPORTED'` and a local of the same name:

| case | expected | got |
| --- | --- | --- |
| `f({ KEY } = {})` | local | local |
| `f({ KEY })` | local | local |
| `f({ a: KEY } = {})` | local | local |
| `f(KEY)` | local | local |
| `f({ KEY = 'D' } = {})` | default | default |
| `f([KEY] = [])` | local | local |
| `f() { return KEY }` (control) | imported | imported |

No regressions — shorthand keeps working because `key === value` there, which the new guard's `parent.value !== child` clause preserves.

Happy to open a PR with the guard plus test cases covering the five affected forms, if that's welcome. Credit to @webbertakken for the original diagnosis; I only verified it and mapped the edges.
