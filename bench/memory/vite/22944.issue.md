# `module-runner`: stack-trace source mapping throws `ReferenceError: Buffer is not defined` when a test realm legitimately lacks `globalThis.Buffer`, masking the original error (issue #22944)

## Environment

- vite `8.0.16` (`dist/node/module-runner.js`)
- vitest `4.1.6` (default `sourcemapInterceptor` path, node environment, worker threads)
- Node.js `v24.16.0`
- macOS (reproduces on any platform)

## Describe the bug

`module-runner.js` has an asymmetric/broken guard around its use of the `Buffer` global, so any error whose `.stack` is prepared while `globalThis.Buffer` is absent is replaced by an uncaught `ReferenceError: Buffer is not defined` — hiding the real failure.

Two spots in `dist/node/module-runner.js` (8.0.16):

1. **L91 — `decodeBase64`: the guard is load-time-only, but the dereference is call-time.**

   ```js
   decodeBase64 = typeof Buffer == "function" && typeof Buffer.from == "function"
     ? (base64) => Buffer.from(base64, "base64").toString("utf-8")
     : (base64) => textDecoder.decode(Uint8Array.from(atob(base64), (c) => c.charCodeAt(0)))
   ```

   The `typeof Buffer` check runs once when the module is evaluated. The selected arrow function still resolves the bare `Buffer` identifier from the global realm **at every call**. If `globalThis.Buffer` is deleted *after* module load, the "guarded" branch throws `ReferenceError`. (The `textDecoder` fallback exists precisely for Buffer-less realms, but it can never be reached in this scenario.)

2. **L868 — `retrieveSourceMap`: entirely unguarded.**

   ```js
   sourceMapData = Buffer.from(rawData, "base64").toString(), sourceMappingURL = source;
   ```

   The inline-source-map decode path has no fallback at all.

Because `module-runner` also installs `Error.prepareStackTrace` in the worker realm (L987 / `interceptStackTrace`) to source-map stacks of evaluated modules, the failure mode is vicious: preparing **any** error's stack while `Buffer` is absent throws from inside `prepareStackTrace` (via `getModuleSourceMapById` → `decodeBase64`), and the original error's report is replaced by the `ReferenceError`.

For maintainers: in source these correspond to `packages/vite/src/module-runner/utils.ts` (`decodeBase64`) and `packages/vite/src/module-runner/sourcemap/interceptor.ts` (`retrieveSourceMap`) — both still present on `main` as of 2026-07-15.

## Why a realm may legitimately lack `Buffer`

Browser-parity tests delete Node-only globals to assert that browser-destined modules don't depend on them, e.g.:

```ts
const backup = globalThis.Buffer;
Reflect.deleteProperty(globalThis, "Buffer");
try {
  await import("./some-web-module.js"); // must work without Buffer in a browser
} finally {
  globalThis.Buffer = backup;
}
```

If anything fails inside that window — most commonly a vitest `testTimeout` under CPU load, since the timeout error's stack is prepared synchronously at timeout time — the genuine failure is masked by the unrelated `ReferenceError`, making the underlying problem much harder to diagnose.

There is precedent for this exact class of bug in this file: a `TextDecoder`-availability failure in the same source-map path was reported as vitest issue #9987 after vite PR #21985 touched it. The `Buffer` usage has the same realm-assumption problem.

## Reproduction

`buffer-mask-repro.test.ts` (~13 lines):

```ts
import { test } from "vitest";

test("timeout during a Buffer-less window gets masked", async () => {
  const backup = globalThis.Buffer;
  Reflect.deleteProperty(globalThis, "Buffer");
  try {
    // Simulates slow work (e.g. dynamic imports under CPU load) that
    // outlives the test timeout while Buffer is deleted.
    await new Promise((resolve) => setTimeout(resolve, 5_000));
  } finally {
    globalThis.Buffer = backup;
  }
}, 100);
```

Command (vitest 4.1.6 / vite 8.0.16 / Node 24, default node environment):

```
npx vitest run buffer-mask-repro.test.ts
```

Deterministic result: alongside the expected `Test timed out in 100ms.`, the run reports an unrelated uncaught exception that masks/pollutes the report.

## Suggested fix

Any of these would resolve it; the first is smallest:

1. Capture `Buffer` at module scope where the runtime supports it (e.g. `import { Buffer } from "node:buffer"` in the node build, or `const NodeBuffer = globalThis.Buffer` at load), and use the captured binding in `decodeBase64` (L91) and `retrieveSourceMap` (L868), so late deletion of the global cannot break stack preparation.
2. Evaluate the `typeof Buffer` guard at call time instead of load time (and add the same guard to L868), falling back to the existing `TextDecoder`/`atob` path.
3. Use the `TextDecoder` implementation unconditionally — it is already required to exist for this file (see the TextDecoder incident above).

Happy to send a PR for option 1 or 2.
