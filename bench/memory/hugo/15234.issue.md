# templates.Defer: identical block bodies in different output formats share one escaping mode, chosen non-deterministically per build (issue #15234)

### What version of Hugo are you using (`hugo version`)?

<pre>
$ hugo version
hugo v0.164.0-[commit removed]+extended windows/amd64 BuildDate=2026-07-06T16:39:30Z VendorInfo=gohugoio
</pre>

### Does this issue reproduce with the latest release?

Yes.

```text
hugo v0.165.0-[commit removed]+extended windows/amd64 BuildDate=2026-08-12T14:26:28Z VendorInfo=gohugoio
```

Over one run of 40 consecutive builds of the unchanged reproduction site below with that binary, 28 builds published the wrong value in `public/index.html` and 12 published the wrong value in `public/index.txt`. All 40 exited 0, and none printed a warning or an error.

### Summary

When two templates belonging to different output formats contain byte-identical `templates.Defer` block bodies, both blocks do execute, each with its own correct output-format context. What they share is the escaping applied inside the block, and which of the two escaping modes survives changes from build to build of an unchanged site. On every build exactly one of the two outputs is therefore wrong: either an HTML page publishes a value raw that it escapes correctly a few characters earlier outside the block, or a plain-text page receives HTML entities.

### Reproduction

Three files in an empty directory. No content, no modules, no external tooling.

`hugo.toml`:

```toml
baseURL = 'https://example.org/'
title = 'defer probe'
disableKinds = ['page', 'section', 'taxonomy', 'term', 'RSS', 'sitemap', 'robotsTXT']

[outputFormats.probe]
mediaType = 'text/plain'
baseName = 'index'
isPlainText = true

[outputs]
home = ['html', 'probe']
```

`layouts/home.html`:

```go-html-template
{{ $v := "<b>&" }}OUT[{{ $v }}]{{ with (templates.Defer (dict "key" "K" "data" (dict "v" $v))) }}IN[{{ .v }}]{{ end }}
```

`layouts/home.probe.txt`, byte-identical to `layouts/home.html` (both md5 `c921197a9c8637852e38d94a0352359d`):

```go-html-template
{{ $v := "<b>&" }}OUT[{{ $v }}]{{ with (templates.Defer (dict "key" "K" "data" (dict "v" $v))) }}IN[{{ .v }}]{{ end }}
```

`OUT[...]` interpolates the value outside the deferred block, `IN[...]` interpolates the same value inside it. Then run `hugo` several times without changing anything, and look at `public/index.html` and `public/index.txt` after each run.

### What I expected

Each format's deferred block rendered under that format's own escaping — `IN[&lt;b&gt;&amp;]` in `public/index.html` and `IN[<b>&]` in `public/index.txt` — and the same result on every build of an unchanged site.

The documentation says "The output format, site, and language will be the same, even if the execution is deferred." The output-format *context* does hold up, as the identity-token control below shows; it is the escaping regime that does not follow the output format.

### Controls

All of these were run at both v0.164.0 and v0.165.0.

**The block really does execute once per output format.** Adding `{{ warnf "DEFER-EXEC-%d" math.Counter }}` to the start of the still byte-identical block body logs two executions in every build:

```text
WARN  DEFER-EXEC-1
WARN  DEFER-EXEC-2
INFO  build:  step render deferred count 2 duration 1.7497ms
--- public/index.html ---
OUT[&lt;b&gt;&amp;]IN[<b>&]
--- public/index.txt ---
OUT[<b>&]IN[<b>&]
```

So this is not one rendering substituted into two files; it is two renderings sharing one escaping mode.

**Different `key` values do not separate them.** With `"KH"` in `layouts/home.html` and `"KT"` in `layouts/home.probe.txt`, the block bodies still byte-identical, the escaping stayed shared and kept flipping: 36 builds, 22 with the HTML page wrong and 14 with the plain-text page wrong.

**Different block body text does separate them, stably.** Changing the body to `INH[{{ .v }}]` in the HTML template and `INT[{{ .v }}]` in the plain-text template gives the correct per-format result in 36 of 36 builds, with no flip: `INH[&lt;b&gt;&amp;]` in `public/index.html` and `INT[<b>&]` in `public/index.txt`.

**The per-format context inside the block is correct.** With the body still byte-identical in both templates, but carrying an output-format identity token next to the value:

```go-html-template
{{ $v := "<b>&" }}OUT[{{ $v }}]{{ with (templates.Defer (dict "key" "K" "data" (dict "v" $v))) }}IN[{{ (index page.AlternativeOutputFormats 0).Name }}|{{ .v }}]{{ end }}
```

With exactly two formats configured the single alternative names the *other* one, so `IN[probe|...]` marks the execution that produced the HTML page and `IN[html|...]` the one that produced the plain-text page. That token was correct in 36 of 36 builds, while the escaping of the value beside it in the very same body was shared and flipped across those builds:

```text
public/index.html   OUT[&lt;b&gt;&amp;]IN[probe|<b>&]
public/index.txt    OUT[<b>&]IN[html|<b>&]

public/index.html   OUT[&lt;b&gt;&amp;]IN[probe|&lt;b&gt;&amp;]
public/index.txt    OUT[<b>&]IN[html|&lt;b&gt;&amp;]
```

### Where this appears to come from

Offered as a lead from reading the source, not as an instrumented finding.

`tpl/tplimpl/templatetransform.go`, `handleWith` (v0.164.0, function at line 409) registers the extracted block under a hash of the block body alone, at lines 450-459:

```go
inner := withNode.List.CopyList()
s := inner.String()
...
innerHash := hashing.XxHashFromStringHexEncoded(s)
deferredID := tpl.HugoDeferredTemplatePrefix + innerHash
...
c.deferNodes[deferredID] = inner
```

Nothing about the owning template, its output format or its media type enters that identifier, so two templates in different output formats with the same body produce the same `deferredID`.

`tpl/tplimpl/templatestore.go`, `addDeferredTemplate` (v0.164.0, function at line 916) then keeps only the first registration under that name, and the first owner fixes the parse namespace for whoever comes later:

```go
if _, found := t.templatesByPath.Get(name); found {
    return nil
}
...
if owner.D.IsPlainText {
    prototype := t.tns.parseText
    ...
} else {
    prototype := t.tns.parseHTML
    ...
}
```

That is exactly the escaping regime the two output formats disagree about, and the loser silently inherits the winner's.

Which owner gets there first looks order-dependent. `transformTemplates` (function at line 1916) reaches the registrations by ranging `s.templates()` at line 1937, and that iterator's inner loop at line 1784 ranges a `map[nodeKey]*TemplInfo` — the value type of `treeMain`, declared at line 447 — whose iteration order Go randomizes per run. I found no sort on that path.

One contrast worth noting: the sibling transform in the same file, `handleWithPartial` (function at line 324), hashes the owning template's name into its identifier at line 335 — `hashing.XxHashFromStringHexEncoded(c.t.Name() + withNodeInnerString)` — while the older defer path does not.

I checked the implicated files at v0.164.0, v0.165.0 and master `[commit removed]`: `tpl/tplimpl/templatestore.go`, `tpl/templates/templates.go` and `tpl/template.go` are byte-identical at all three, and `tpl/tplimpl/templatetransform.go` differs at master only outside this path — the `handleWith` lines quoted above are unchanged there, at 405-414.

### A constraint on any fix

Hashing the owning template's name into the deferred identifier, the way `handleWithPartial` does, would break something the documentation promises for `key`: "This will, combined with a hash of the template content, be used as a cache key." Two *different layouts of the same output format* with identical bodies and one shared key share a single execution today, and that is worth keeping — at both versions, on a variant of the site above reduced to one output format and with the `page` kind enabled plus one content file, so that `single.html` renders at all, I measured a single `DEFER-EXEC-1` for a `home.html` and a `single.html` written that way, with both pages publishing the shared result.

Separating registrations by the property that actually differs here — the owner's `IsPlainText`, or its output format — would fix the escaping while leaving that documented same-format sharing untouched.

### Related, not duplicates

- #7774, fixed by #8462 ("Fixes #7774", merged 2021-04-23): per-build nondeterminism in output-format template lookup for shortcodes. Same failure shape, different subsystem, and it predates `templates.Defer`.
- #13236: two empty deferred blocks *in the same template* collided on the identifier `__hdeferred/cafc7706cee4572b` and panicked; closed as completed. That is the same body-only identifier, in a different situation — the collision there is inside one template, and the cross-output-format escaping consequence does not come up.

I did not find an existing report covering byte-identical `templates.Defer` bodies across output formats.

### What I did not establish

- **Which registration wins in any individual build.** I inferred the winner from the escaping in the published output; I did not instrument the running binary to observe the registration.
- **Platform generality.** Everything above was measured on one machine, Windows 11, amd64 extended builds. Whether the split differs on another platform or core count is unmeasured.
- **Two non-plain-text formats sharing a body.** The escaping observable needs an `isPlainText` format paired with an HTML one, so two HTML-ish formats sharing a body were not tested and the reach across format combinations is unknown.
